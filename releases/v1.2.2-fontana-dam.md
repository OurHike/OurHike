# v1.2.2 — Fontana Dam

_21 changes since v1.2.1._

v1.2.1 finished the day-hike builder's map and gave it the White Mountains to plan
on. This release makes the builder route the way the rest of the app already loads
data: the trail network it snaps to now arrives in the same 1°-square cells the
corridor and DEM archives use, instead of needing one graph covering everywhere
before it can answer a single tap — and those same cells are what let USFS's, NH
GRANIT's and NYS's trails reach the builder for the first time, not just the map.
Alongside that: two findings v1.2.1's own release review deferred are fixed, a gap
that release flagged in its own notes (USFS's trailheads showing as parking) is
closed, and a stuck download request now falls back to what the phone already has
instead of hanging.

**Why a patch, and stated plainly rather than left for a reader to notice.**
Measured against §4's rule — PATCH is fixes only, no new behaviour — several of
the changes below are new behaviour: the day-hike builder routing over a
cell-loaded network graph, other organizations' trails reaching the builder for
the first time, network tiles riding along with stretch downloads. By the letter
of §4 this reads closer to MINOR. It ships as v1.2.2 by the maintainer's
deliberate call rather than by the rule — the same call v1.2.1 made about its own
MINOR-shaped content, for the same reason: nothing here strains a hiker's
understanding of what a patch number means the way a schema change or a required
re-install would, every one of these is additive or a fix to something already
shipped, and the version number is the maintainer's decision to own, not this
document's to relitigate.

## What changed for a hiker

**Planning a day hike**

- The day-hike builder loads the trail network it routes over in pieces. Opening
  the builder used to need the whole network graph before it could answer a
  single tap; now it loads the same 1°-square cells the map already uses for
  offline downloads, so it's ready as soon as the ground under you has arrived,
  not the whole corridor.
- USFS's, NH GRANIT's and NYS's trails and waypoints — added to the map itself in
  v1.2.1 — can now be routed over in the day-hike builder too, not just seen.
- A day hike whose route crosses a real gap in the trail network now shows that
  gap in the route list, not only on the map.
- Nameless stream crossings are carried correctly across an upstream trail
  re-measurement.
- Amenity waypoints (parking, vistas and the like) are held to the same corridor
  boundary the water points already use, so a stray far-off one doesn't appear.

**More trails and waypoints**

- USFS's 7,358 trailheads show as trailheads. v1.2.1 introduced the Trailhead pin
  but left this larger population showing as plain parking — [#1218](https://github.com/OurHike/OurHike/issues/1218),
  named in v1.2.1's own notes as a present-tense gap, is closed.

**Downloads**

- The stretch-download option (v1.2.1) now carries the trail network layer with
  it, not only the ground under it.
- A download request that stalls now falls back to what's already on the phone
  instead of hanging.

**Recording where you actually are**

- Turning the screen on and off quickly while GPS is still acquiring a lock no
  longer leaves the wake lock in an inconsistent state.

**One merged pull request landed after this pass and is not covered by it:**
[#1272](https://github.com/OurHike/OurHike/pull/1272), which re-applied #1258's
"carry nameless crossings" change (already reviewed and already in the table
above and the hiker-facing list) after an earlier revert, and regenerated
`pipeline/reference/poi_identity.json` to match. Not re-reviewed here because
its own body already carries the equivalent evidence a review would ask for:
the code half is a verbatim re-application of already-reviewed code with "no
published byte changes" by its own account, and the ledger half is a generated
file whose diff is 5,357 rows each gaining one field (`stream_id`) with zero
ids added, removed, retired or un-retired — checked field-by-field against
`main` in the PR body rather than asserted. `scripts/test.sh` was green on its
final head. If that account turns out to be wrong, it is exactly the kind of
finding a hiker's safety would turn on (§8b's water set), so it is named here
rather than folded silently into the "fixed" count above.

**The one fixed:** the day-hike builder's draw-a-stroke handler silently dropped
the stroke, with no feedback, if it was drawn before any trail-network cell had
ever loaded — a narrow window at the very start of a session. The sibling tap
handler already had the correct guard (show `NETWORK_STILL_ARRIVING` rather than
returning early) and the stroke handler was simply missing it; the fix mirrors
the tap handler's logic exactly. **No new automated test was added for it.** The
failure window (before any graph shard has ever loaded) is narrow to construct
in the existing `App`-integration harness, and CLAUDE.md's own standard for this
suite is that an ordering-sensitive test is run three times before it's trusted
— a bigger investment than this session made for a one-line parity fix already
verified by hand against the tap handler's own, already-tested logic. Worth
someone adding properly rather than rushed here.

**The two deferred, and why neither is §8b's safety-critical set:**

- **[#1274](https://github.com/OurHike/OurHike/issues/1274) — a followed hike's climb/highlight can be wiped to null by a
  transient fetch failure on an unrelated, brand-new cell.** The map still draws,
  position is still correct, and reverting to "no figures for this hike" is the
  same honest-unknown state the code already treats as legitimate elsewhere — the
  comment above the effect in question explicitly prefers that over a highlight
  that silently stops short at a cell boundary. What's missing is a retry after a
  transient failure, which needs a deliberate design pass (distinguishing "this
  cell's data doesn't exist" from "the fetch failed this once"), not a quick
  patch under release-train time pressure.
- **[#1275](https://github.com/OurHike/OurHike/issues/1275) — every new trail-graph cell merge re-fetches and re-hashes every
  previously-merged cell's geometry and elevation, not just the new one.** Pure
  efficiency, not correctness: wasted mobile data and CPU over the course of a
  multi-day hike as cells accumulate, worth fixing with an in-memory cache keyed
  by cell rather than a rushed patch.

## Compatibility

**Nothing is required of anyone.** No re-install, no re-download, no signing in
again. This release adds no database migration — there are no new revisions
under `backend/alembic/versions/` since v1.2.1 — and touches no backend code at
all (`git diff --name-status v1.2.1..HEAD -- backend/` is empty), so the OpenAPI
baseline added for this release (`backend/openapi_baselines/v1.2.2.json`) is
byte-identical to v1.2.1's.

The new trail-graph and network-tile caches this release adds are deliberately
outside `client/src/lib/storedShapes.fixtures.ts`'s compatibility ledger, per
that file's own stated rule: they hold published bytes behind a manifest hash,
and a reader that can't make sense of one drops it and re-fetches rather than
needing to keep reading an old shape. That costs signal, not a hiker's own work,
which is the line §8c draws — not a gap, and not new to this cycle.

**Two upstreams remain unverifiable, and this is a standing gap rather than a
new one.** The "Upstream data freshness" tracker ([#478](https://github.com/OurHike/OurHike/issues/478)) shows `topo_quads` and
`atc_trail_updates` as "could not be checked" as of this release — first seen
2026-08-09 and 2026-08-13 respectively, both predating v1.2.0. Nothing is
flagged as actually changed upstream this cycle; the gap is that two sources
cannot currently confirm either way.
